# Dimension Tokens

> Semantic dimension tokens — every length-based value in the system, covering both sizing (the element itself, mainly `ui_scale`) and spacing (gaps between or around elements, mainly `density` and `typography_context`). Surface in CSS with px or rem units preserved.
>
> *(`ob.s.dimension.token_family_docs.$description` — [`03_semantic/dimension/density/static.json`](../../src/lib/themes/03_semantic/dimension/density/static.json))*

## At a glance

| Layer | Path | Source files | Purpose |
|---|---|---|---|
| **Primitive** | `ob.p.dimension.px.*` | [`02_primitive/dimension.json`](../../src/lib/themes/02_primitive/dimension.json) | Atomic length values, px only. Not for direct consumption. |
| **Semantic** | `ob.s.dimension.{static\|dynamic}.*` | [`03_semantic/dimension/{group}/{mode}.json`](../../src/lib/themes/03_semantic/dimension) for the `.px` tokens, [`03_semantic/dimension/rem/{density,ui_scale}/{mode}.json`](../../src/lib/themes/03_semantic/dimension/rem) for the `.rem` tokens | Named tokens organised by 4 mode groups. |
| **Component** | (per-component) | various | Consumes semantic dimension tokens. |

The live visual reference is the Figma page **`Dimension – Spacing & Sizing`** in `DesignSystem@Tokens V9.9`, generated by [`scripts-custom/figma-doc-builders/dimension/build-dimension.js`](../../scripts-custom/figma-doc-builders/dimension/build-dimension.js).

## Primitive layer

| Scale | Path | Count | Keying |
|---|---|---|---|
| Absolute px | `ob.p.dimension.px.<N>` | 27 | Key `<N>` is the px count itself (`8` → `8px`). |

There is no parallel `rem` primitive scale. The `rem` variant is computed at the **semantic** level from the `px` value (`{...px} / 16 * 1rem`), not stored as a separate primitive.

- **`px`** — absolute, does not scale with the user's browser font-size setting. Use for elements that must render pixel-perfect: borders, fine lines, icons.
- **`rem`** — fluid, relative to the root `<html>` font size. Required for accessibility — scales with user preferences.

The primitive layer has px only. The semantic layer holds each `ui_scale` and `density` step as a `.px` token and, for now, a `.rem` sibling computed from it. Which unit a value gets in CSS follows the rule in the [Token Usage Guide](../05-reference/01-token-usage-guide.md#px-vs-rem--which-unit-when-building-a-component): tokens are px, and the CSS build, which the developers maintain, is meant to convert to rem where rem is better for CSS (not implemented yet).

> Primitives are atomic and context-agnostic. They must not be consumed directly by components.

## Semantic layer: 4 groups

Semantic dimension tokens are split into four orthogonal **groups**. Three of them (`density`, `ui_scale`, `typography_context`) have a `static` flavour (constant across modes) plus 1+ dynamic mode files; `viewport` is mode-only — every viewport size is itself a mode, with no separate static file.

| Group | Static file | Dynamic modes | Primary use |
|---|---|---|---|
| `density` | `density/static.json` | `compact.json`, `standard.json`, `spacious.json` | **spacing** — between elements |
| `ui_scale` | `ui_scale/static.json` | `sm.json`, `md.json`, `lg.json` | **sizing** — of elements themselves |
| `typography_context` | `typography_context/static.json` | `interface.json`, `prose.json` | **spacing** — vertical padding around typography |
| `viewport` | *(none)* | `xs.json`, `sm.json`, `md.json`, `lg.json`, `xl.json`, `2xl.json` | **sizing** — min/max width of the page container, per viewport |

### Static vs dynamic

- **Static** tokens point to a primitive directly: `"$value": "{ob.p.dimension.px.4}"`. They do not change when the mode switches.
- **Dynamic** tokens belong to one of the mode files for their group. Switching the active mode re-resolves the same token name to a different primitive (Style Dictionary "last file wins" mode resolution).

Both flavours emit a plain CSS custom property at the consumption site — the dynamic switch happens entirely at build / load time.

## `density` — spacing between elements

> Density-independent spacing tokens — fixed values not affected by density mode. Use: for spacing that must remain constant regardless of density. Avoid: for spacing that should compress in compact or expand in spacious mode.
>
> *(`$description` from `density/static.json`)*

- **Static**: 30 tokens — 15 sizes × `{px, rem}` (the `.px` tokens in `density/static.json`, the `.rem` tokens in `rem/density/static.json`). Sizes follow a single t-shirt + numeric scale:

  | Bucket | Sizes |
  |---|---|
  | Base scale | `xs, sm, md, lg, xl` |
  | Extended scale | `2xl, 3xl, 4xl, … , 11xl` |

- **Dynamic** (3 modes): same 15-size scale; each token name resolves to a different primitive depending on the active density mode:
  - `compact.json` — tighter spacing
  - `standard.json` — balanced spacing for general-purpose layouts
  - `spacious.json` — generous spacing

See [`../04-modes/05-density.md`](../04-modes/05-density.md) for mode mechanics.

---

## `ui_scale` — sizing of elements

> Fixed component dimensions (UI Scale) — values that remain constant across all size modes. Use: for dimensions that must not scale between size modes. Avoid: for dimensions that should respond to UI Scale changes.
>
> *(`$description` from `ui_scale/static.json`)*

Organised into **7 magnitude buckets**, ordered by px range (data-derived):

| Bucket | px range | Sizes present | Purpose |
|---|---|---|---|
| `none` (top-level) | 0 | (single value × `px`/`rem`) | Zero / collapse / reset. |
| `micro` | 1–3 | `xs sm md` | Hairlines, sub-pixel rules, fine borders. |
| `element` | 4–12 | `xs sm md lg xl` | Individual element dimensions. |
| `spacing` | 16–32 | `xs sm md lg xl` | Inline-element widths. |
| `container` | 36–64 | `xs sm md lg xl` | Container sizing. |
| `layout` | 80–192 | `xs sm md lg xl` | Page-level layout sizing. |
| `macro` | 256+ | `xs sm` | Large-scale dimensions. |

Each `bucket × size` pair has both `px` and `rem` variants.

- **Static**: fixed values that do not respond to UI Scale mode changes.
- **Dynamic** (3 modes): values typically derived from primitives × multiplier:
  - `sm.json` — Small UI Scale
  - `md.json` — Medium UI Scale (default)
  - `lg.json` — Large UI Scale

See [`../04-modes/03-ui-scale.md`](../04-modes/03-ui-scale.md) for mode mechanics.

## `typography_context` — vertical padding around typography

> Fixed vertical spacing for HTML typography elements — padding-top and padding-bottom values for headings and paragraphs. Static because this surrounding spacing remains constant regardless of typography context mode (interface vs prose).
>
> *(`$description` from `typography_context/static.json`)*

Sizes: 9 steps (`none, xs, sm, md, lg, xl, 2xl, 3xl, 4xl`). **No `px`/`rem` split** — each token is single-valued; `$type` is `spacing` (Tokens Studio unofficial type that compiles to `dimension` on export).

Tokens are consumed as padding on specific selectors (`h1–h6`, `p`, `p_lead`). Each token's `$description` records which selector consumes it — e.g.:

- `xs` — minimal vertical spacing. Consumed as bottom padding on all headings (`h1–h6`).
- `sm` — small vertical spacing. Consumed as top padding on subheadings (`h2–h6`) and bottom padding on paragraphs.
- `2xl` — generous vertical spacing. Consumed as bottom padding on lead paragraphs (`p_lead`).

- **Static**: fixed across the typography-context mode switch.
- **Dynamic** (2 modes):
  - `interface.json` — compact spacing tuned for UI controls and labels.
  - `prose.json` — generous spacing tuned for long-form reading.

See [`../04-modes/04-typography-context.md`](../04-modes/04-typography-context.md) for mode mechanics.

## `viewport` — page-container width per viewport

> Min/max width for the page-container component, per viewport. Mode-scoped: each of the six viewport modes resolves `min_width` and `max_width` to its own range.
>
> *(`$description` pattern from `viewport/xs.json`)*

- **No static flavour** — every viewport size is itself a mode; there is no viewport-independent constant. 6 modes × 2 tokens (`min_width`, `max_width`) = 12 tokens.
- **Modes**: `xs.json`, `sm.json`, `md.json`, `lg.json`, `xl.json`, `2xl.json`, one file per viewport range. `xl` is the base viewport.
- Values reference the `viewport` mode collection at the global tier (`ob.g.mode_collection.viewport.*`), not a dimension primitive directly. `min_width` resolves to the range's `from` (the `xs` floor resolves to `min_supported_width` instead); `max_width` resolves to its `to`. `2xl` is open-ended, so its `max_width` is a `99999px` sentinel.

See [`../04-modes/06-viewport.md`](../04-modes/06-viewport.md) for mode mechanics and the full breakpoint table.

## px and rem at the semantic layer

Each `ui_scale` and `density` step exists as two tokens:

- `ob.s.dimension.static.density.md.px` → `{ob.p.dimension.px.8}` (always 8 px)
- `ob.s.dimension.static.density.md.rem` → `{ob.s.dimension.static.density.md.px} / 16 * 1rem` (computed from the `.px` sibling, always 0.5 rem ≡ 8 px at root font-size 16)

The `.px` token and the `.rem` token of one step are in two different files. The `.rem` tokens are in the folder [`03_semantic/dimension/rem/`](../../src/lib/themes/03_semantic/dimension/rem). It mirrors the `.px` files: `rem/density/{static,compact,standard,spacious}.json` and `rem/ui_scale/{static,sm,md,lg}.json`. A `.rem` token is in the file with the same relative path as the file of its `.px` token. The `rem` folder is not a fifth group. The three mode files of a group hold the same `.rem` formulas, because each formula points to the `.px` token of the active mode. When you change a `.rem` token, change it in every mode file of its group, so that the copies stay equal.

Every file in the `rem` folder has the status `source` in Tokens Studio. The tokens resolve and go into the CSS build, but they do not become Figma variables. The Figma page `Dimension – Spacing & Sizing` therefore has no `.rem` rows.

The unit in CSS follows the use (details in the [Token Usage Guide](../05-reference/01-token-usage-guide.md#px-vs-rem--which-unit-when-building-a-component)):

| Use | Unit in CSS |
|---|---|
| Body text, content padding, scalable layouts, anything that should respect user font-size preferences | **rem** |
| Borders, dividers, icons, anything pixel-perfect | **px** |

`typography_context` has no `.px`/`.rem` pair: each token is one px value (it aliases `ob.p.dimension.px.*`). In CSS it is a rem group once the build converts; until then it is px.

## Naming conventions

```
ob.p.dimension.<unit>.<key>                                 primitive
ob.s.dimension.<flavour>.<group>.[<bucket>.]<size>[.<unit>] semantic
```

- `<flavour>` ∈ `static | dynamic`
- `<group>` ∈ `density | ui_scale | typography_context` (`viewport` doesn't use this pattern — see below)
- `<bucket>` only present in `ui_scale` (one of the 7 buckets above)
- `<size>` ∈ `none, xs, sm, md, lg, xl, 2xl, … , 11xl` (subset depends on group)
- `<unit>` ∈ `px | rem` — present in `density` and `ui_scale`; absent in `typography_context`

`viewport` has no `<flavour>` segment: its path is `ob.s.dimension.viewport.<min_width|max_width>`, and the six per-viewport files (`xs.json` … `2xl.json`) each supply the value for that same token name in their own mode.

The Figma reference page sorts tokens within each table by **size magnitude** (`none → micro → element → spacing → container → layout → macro` for ui_scale; `xs → sm → … → 11xl` for density), so a designer reads the table top-to-bottom from smallest to largest.

## Live reference

The build script reads these JSON files via Figma variables and writes a timestamped reference page to V9.9. The page is provenance-stamped (date, script@gitSha, source file, row count, errors, duration) and laid out in two columns: **static** on the left, **dynamic** on the right.

```bash
node scripts-custom/figma-doc-builders/dimension/build-dimension.js              # build everything + validate
node scripts-custom/figma-doc-builders/dimension/build-dimension.js --table density-static
node scripts-custom/figma-doc-builders/dimension/build-dimension.js --validate   # validate only, no writes
```

Building blocks (the row / section_bar / preview_bar masters consumed by the script) live on the `Utilities` page under `_building_blocks/dimension`.
